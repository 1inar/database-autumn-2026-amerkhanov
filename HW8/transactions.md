# HW7 — Транзакции и уровни изоляции

## 1. Подготовка

```sql
-- Таблица авторов: вторая таблица будет хранить стихи автора.
DROP TABLE IF EXISTS tx_demo_poems;
DROP TABLE IF EXISTS tx_demo_authors;

CREATE TABLE tx_demo_authors (
    author_id  integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    author_name text NOT NULL,
    poem_count integer NOT NULL DEFAULT 0 CHECK (poem_count >= 0)
);

CREATE TABLE tx_demo_poems (
    poem_id    integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    author_id  integer NOT NULL REFERENCES tx_demo_authors(author_id),
    title      text NOT NULL,
    created_at timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP
);

INSERT INTO tx_demo_authors (author_id, author_name, poem_count)
VALUES
    (1, 'Тестовый автор 1', 0),
    (2, 'Тестовый автор 2', 0)
ON CONFLICT (author_id) DO UPDATE
SET author_name = EXCLUDED.author_name,
    poem_count = EXCLUDED.poem_count;

SELECT * FROM tx_demo_authors ORDER BY author_id;
SELECT * FROM tx_demo_poems ORDER BY poem_id;
```


## 2. Базовые операции с транзакциями

### 2.1. BEGIN … COMMIT: добавление стихотворения и обновление автора

**Сценарий 1 — успешная фиксация.**

```sql
BEGIN;

-- Добавляем стихотворение.
INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Стихотворение, зафиксированное COMMIT');

-- Обновляем связанную запись автора.
UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 1;

-- Проверяем изменения внутри транзакции.
SELECT * FROM tx_demo_poems WHERE author_id = 1;
SELECT * FROM tx_demo_authors WHERE author_id = 1;

COMMIT;

-- Проверяем данные после фиксации.
SELECT * FROM tx_demo_poems WHERE author_id = 1;
SELECT * FROM tx_demo_authors WHERE author_id = 1;
```

**Ожидаемый результат:** стихотворение сохранено, `poem_count` автора увеличен на 1. Обе операции зафиксированы вместе.

**Сценарий 2 — повтор операции с откатом.**

```sql
BEGIN;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (2, 'Стихотворение, которое будет отменено');

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 2;

-- Внутри транзакции обе операции видны.
SELECT * FROM tx_demo_poems WHERE author_id = 2;
SELECT * FROM tx_demo_authors WHERE author_id = 2;

ROLLBACK;

-- После отката вставленной записи нет, счётчик прежний.
SELECT * FROM tx_demo_poems WHERE author_id = 2;
SELECT * FROM tx_demo_authors WHERE author_id = 2;
```

**Ожидаемый результат:** после `ROLLBACK` новая запись отсутствует, а значение `poem_count` возвращается к состоянию до транзакции.

### 2.2. Ошибка внутри транзакции

В PostgreSQL ошибка выполнения SQL-команды переводит текущую транзакцию в состояние aborted. До `ROLLBACK` выполнять обычные SQL-команды в ней нельзя.

**Сценарий 1 — ошибка деления на ноль после изменений.**

```sql
BEGIN;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Запись перед ошибкой');

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 1;

-- Намеренная ошибка: division by zero.
SELECT 10 / 0;

-- Эта команда не выполнится, пока транзакция aborted.
SELECT * FROM tx_demo_poems WHERE title = 'Запись перед ошибкой';

ROLLBACK;

-- Проверяем: вставка и UPDATE отменены.
SELECT * FROM tx_demo_poems WHERE title = 'Запись перед ошибкой';
SELECT * FROM tx_demo_authors WHERE author_id = 1;
```

**Ожидаемый результат:** PostgreSQL сообщает `division by zero`. После `ROLLBACK` отменяются и `INSERT`, и `UPDATE`, выполненные до ошибки.

**Сценарий 2 — ошибка ограничения целостности.**

```sql
BEGIN;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Ещё одна запись перед ошибкой');

UPDATE tx_demo_authors
SET poem_count = -100
WHERE author_id = 1;

COMMIT;

ROLLBACK;

SELECT * FROM tx_demo_poems
WHERE title = 'Ещё одна запись перед ошибкой';
SELECT * FROM tx_demo_authors WHERE author_id = 1;
```

**Ожидаемый результат:** PostgreSQL сообщает о нарушении `CHECK constraint`. Транзакция не фиксируется; после `ROLLBACK` вставленная запись также исчезает.

## 3. Уровни изоляции

### 3.1. READ UNCOMMITTED

В PostgreSQL уровень `READ UNCOMMITTED` фактически работает как `READ COMMITTED`. Поэтому **грязное чтение невозможно**: транзакция не увидит незакоммиченные изменения другой транзакции.

Перед каждым сценарием можно вернуть исходное значение:

```sql
UPDATE tx_demo_authors SET poem_count = 0 WHERE author_id = 1;
```

**Сценарий 1 — проверка грязного чтения.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

UPDATE tx_demo_authors
SET poem_count = 77
WHERE author_id = 1;

SELECT poem_count FROM tx_demo_authors WHERE author_id = 1;
```

T2 (пока T1 не завершена):

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

COMMIT;
```

T1:

```sql
ROLLBACK;
```

**Ожидаемый результат:** T1 видит `77`, а T2 видит прежнее зафиксированное значение `0`, а не `77`. После отката T1 значение остаётся `0`.

**Сценарий 2 — UPDATE без COMMIT в T1 и чтение в T2.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

UPDATE tx_demo_authors
SET poem_count = 15
WHERE author_id = 1;

```

T2:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

COMMIT;
```

T1:

```sql
ROLLBACK;
```

**Ожидаемый результат:** T2 не читает незакоммиченное значение `15`. В PostgreSQL `READ UNCOMMITTED` не даёт грязного чтения и эквивалентен `READ COMMITTED`.

### 3.2. READ COMMITTED

В PostgreSQL это уровень изоляции по умолчанию. Каждый отдельный `SELECT` видит снимок данных на момент начала именно этого оператора.

**Сценарий 1 — неповторяющееся чтение.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

COMMIT;
```

T2 (между двумя SELECT в T1):

```sql
BEGIN;
UPDATE tx_demo_authors
SET poem_count = poem_count + 10
WHERE author_id = 1;
COMMIT;
```

**Ожидаемый результат:** второй `SELECT` в T1 видит новое зафиксированное значение. Два чтения одной строки в одной транзакции могут вернуть разные результаты — это неповторяющееся чтение.

**Сценарий 2 — чтение после UPDATE другой транзакции.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;

SELECT author_name, poem_count
FROM tx_demo_authors
WHERE author_id = 2;

SELECT author_name, poem_count
FROM tx_demo_authors
WHERE author_id = 2;

COMMIT;
```

T2:

```sql
BEGIN;
UPDATE tx_demo_authors
SET poem_count = poem_count + 5
WHERE author_id = 2;
COMMIT;
```

**Ожидаемый результат:** первый запрос T1 показывает старое значение, второй — обновлённое после `COMMIT` в T2.

### 3.3. REPEATABLE READ

В PostgreSQL все обычные `SELECT` в транзакции `REPEATABLE READ` используют один снимок, установленный первым оператором, которому нужен снимок. Поэтому изменения, зафиксированные другой транзакцией после этого момента, не становятся видны текущей транзакции.

**Сценарий 1 — T1 не видит UPDATE из T2 до завершения.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

COMMIT;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;
```

T2:

```sql
BEGIN;
UPDATE tx_demo_authors
SET poem_count = poem_count + 20
WHERE author_id = 1;
COMMIT;
```

**Ожидаемый результат:** оба `SELECT` внутри T1 показывают одинаковое старое значение. После `COMMIT` T1 новый отдельный `SELECT` видит обновлённое значение.

**Сценарий 2 — попытка показать фантомное чтение через INSERT.**

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

SELECT poem_id, title
FROM tx_demo_poems
WHERE title LIKE 'Фантом-%'
ORDER BY poem_id;

SELECT poem_id, title
FROM tx_demo_poems
WHERE title LIKE 'Фантом-%'
ORDER BY poem_id;

COMMIT;

SELECT poem_id, title
FROM tx_demo_poems
WHERE title LIKE 'Фантом-%'
ORDER BY poem_id;
```

T2:

```sql
BEGIN;
INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Фантом-тест');
COMMIT;
```

**Ожидаемый результат в PostgreSQL:** второй `SELECT` внутри T1 не видит новую строку, хотя T2 уже выполнила `COMMIT`. После завершения T1 новый запрос видит вставленную строку. Таким образом, в PostgreSQL `REPEATABLE READ` предотвращает фантомное чтение благодаря снимку транзакции (это строже минимальных требований стандарта SQL для данного уровня).

### 3.4. SERIALIZABLE

`SERIALIZABLE` — самый строгий уровень изоляции PostgreSQL. СУБД отслеживает зависимости между параллельными транзакциями. Если их нельзя безопасно представить как последовательное выполнение, одна из транзакций завершается ошибкой сериализации. Не каждый параллельный `INSERT` одинаковых данных обязательно приводит именно к `could not serialize access`: при наличии `UNIQUE` может возникнуть обычная ошибка уникальности. Поэтому ниже используются два разных эксперимента.

**Сценарий 1 — две транзакции пытаются вставить одинаковое логическое значение.**

Для демонстрации добавим уникальность названия в тестовой таблице:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS tx_demo_poems_title_uq
ON tx_demo_poems (title);
```

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Одинаковое название');
```

T2:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (2, 'Одинаковое название');

```

T1:

```sql
COMMIT;
```

T2: дождитесь результата. Если PostgreSQL вернул ошибку уникальности (`duplicate key value violates unique constraint`), завершите неудачную транзакцию:

```sql
ROLLBACK;
```

**Ожидаемый результат:** одинаковое название не может быть сохранено дважды из-за `UNIQUE`. В зависимости от порядка выполнения и блокировок конфликт может проявиться как ожидание, а затем нарушение уникальности. Сам по себе этот сценарий демонстрирует ограничение уникальности, а не гарантированную ошибку сериализации.

**Сценарий 2 — ошибка `could not serialize access due to concurrent update`.**

Сначала убедитесь, что автор с `author_id = 1` существует.

T1:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

SELECT poem_count
FROM tx_demo_authors
WHERE author_id = 1;

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 1;


```

T2:

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 1;

COMMIT;
```

T1:

```sql
COMMIT;
```

**Ожидаемый результат:** при таком порядке T1 пытается обновить строку, которую после снимка T1 уже изменила и зафиксировала T2. PostgreSQL отменяет одну из конфликтующих транзакций с ошибкой сериализации (обычно `could not serialize access due to concurrent update`). Выполните `ROLLBACK` в сессии, получившей ошибку.

> После ошибки сериализации приложение должно повторить **всю транзакцию с самого начала**, а не только последнюю SQL-команду.

## 4. SAVEPOINT

`SAVEPOINT` создаёт точку внутри транзакции, к которой можно частично откатиться. Изменения до точки сохраняются в рамках транзакции, а изменения после неё могут быть отменены отдельно. Окончательно данные сохраняются только после `COMMIT`.

**Сценарий 1 — одна точка сохранения.**

```sql
BEGIN;

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 1;

SAVEPOINT before_second_change;

INSERT INTO tx_demo_poems (author_id, title)
VALUES (1, 'Будет отменено через SAVEPOINT');

ROLLBACK TO SAVEPOINT before_second_change;

SELECT * FROM tx_demo_authors WHERE author_id = 1;
SELECT * FROM tx_demo_poems
WHERE title = 'Будет отменено через SAVEPOINT';

COMMIT;

SELECT * FROM tx_demo_authors WHERE author_id = 1;
SELECT * FROM tx_demo_poems
WHERE title = 'Будет отменено через SAVEPOINT';
```

**Ожидаемый результат:** увеличение `poem_count` сохраняется после `COMMIT`, а вставленное после точки стихотворение отменяется.

**Сценарий 2 — две точки сохранения и откат к каждой.**

```sql
BEGIN;

UPDATE tx_demo_authors
SET poem_count = poem_count + 1
WHERE author_id = 2;

SAVEPOINT sp_first;

UPDATE tx_demo_authors
SET poem_count = poem_count + 10
WHERE author_id = 2;

SAVEPOINT sp_second;

UPDATE tx_demo_authors
SET poem_count = poem_count + 100
WHERE author_id = 2;

SELECT poem_count FROM tx_demo_authors WHERE author_id = 2;

ROLLBACK TO SAVEPOINT sp_second;
SELECT poem_count FROM tx_demo_authors WHERE author_id = 2;

ROLLBACK TO SAVEPOINT sp_first;
SELECT poem_count FROM tx_demo_authors WHERE author_id = 2;

COMMIT;

SELECT poem_count FROM tx_demo_authors WHERE author_id = 2;
```

**Ожидаемый результат:** после первого отката остаётся прибавка `+11`, после второго — только `+1`. `COMMIT` фиксирует итоговое значение.

## 5. Выводы

1. `BEGIN` начинает транзакцию, `COMMIT` фиксирует все её изменения, а `ROLLBACK` отменяет их. Это позволяет выполнять связанные операции атомарно.
2. В PostgreSQL ошибка SQL-команды прерывает текущую транзакцию. Чтобы продолжить работу, нужно выполнить `ROLLBACK` или откатиться к точке сохранения, созданной до ошибки.
3. `READ UNCOMMITTED` в PostgreSQL эквивалентен `READ COMMITTED`: грязное чтение не допускается.
4. При `READ COMMITTED` каждый оператор получает новый снимок данных, поэтому повторное чтение может вернуть уже обновлённое значение.
5. При `REPEATABLE READ` транзакция работает с согласованным снимком: изменения и новые строки, зафиксированные конкурентной транзакцией после создания снимка, не видны до завершения текущей транзакции.
6. `SERIALIZABLE` предотвращает аномалии сериализации, отменяя одну из конфликтующих транзакций. После ошибки сериализации нужно повторить всю транзакцию.
7. `SAVEPOINT` позволяет отменить часть операций, не откатывая всю транзакцию. Изменения до точки сохранения остаются, но окончательно фиксируются только через `COMMIT`.
