# Нормализация базы данных "Платформа для поэтов"

## 1. Анализ исходных таблиц

Все исходные таблицы проекта (`users`, `genres`, `poems`, `poem_genres`, `comments`, `ratings`) изначально спроектированы в **3НФ и НФБК**:

## 2. Придумаем сами. Пример 1: Нарушение 2НФ и 3НФ (объединённая таблица стихов)

### Схема (плохая)
poems_bad(poem_id, title, poem_text, author_name, author_email, genre_name, publication_date)

### FD
- poem_id → title, poem_text, publication_date
- author_name → author_email
- (poem_id, genre_name) → ...

### Аномалии
- **Вставки:** нельзя добавить автора без его стихотворения.
- **Обновления:** смена email автора требует обновления всех его строк.
- **Удаления:** удаление последнего стиха удаляет данные об авторе.
- **Избыточность:** имя/email дублируются для каждого стиха.
- **2НФ:** частичная зависимость title/poem_text от poem_id (часть составного ключа).
- **3НФ:** poem_id → author_name → author_email (транзитивная зависимость).

### Решение
Декомпозиция на `users`, `poems`, `genres`, `poem_genres`.

---

## 3. Пример 2: Нарушение НФБК (таблица оценок с названием стиха)

### Схема (плохая)
ratings_bad(user_id, poem_title, author_name, score)
Ключ: (user_id, poem_title)

### FD
- (user_id, poem_title) → score, author_name
- poem_title → author_name  ← детерминант не суперключ

### Аномалии
- **Вставки:** нельзя сохранить автора стиха без оценки.
- **Обновления:** смена автора стиха требует обновления всех оценок.
- **Одноимённые стихи:** ключ не различает разные стихи с одинаковым названием.
- **Нарушение НФБК:** poem_title → author_name, но poem_title не суперключ.

### Решение
Декомпозиция на `poems(poem_id, title, author_id, ...)` и `ratings(rating_id, user_id, poem_id, score)`.

---

## 4. Итог
После декомпозиции все таблицы приведены к 3НФ и НФБК. Аномалии вставки, обновления и удаления устранены, избыточность данных минимизирована.
